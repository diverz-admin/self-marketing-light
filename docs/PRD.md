# Product Requirements Document (PRD): Self-Marketing Platform

## 1. 프로젝트 개요 (Overview)
* **서비스명**: Self-Marketing Platform (셀프 마케팅 플랫폼)
* **목적**: 개발자, 디자이너, 마케터 등 지식 근로자들이 자신의 이력, 포트폴리오, 프로젝트 성과, 업무 인사이트를 스스로 홍보하고 관리할 수 있는 맞춤형 마이 브랜딩 페이지 웹 서비스.
* **타겟 사용자**: 
  - 이직/구직을 준비하는 개발자 및 직군 전문가
  - 개인 프로젝트나 프리랜서 서비스를 홍보하려는 1인 창업가
  - 자신의 배움과 인사이트를 아카이빙하고 공유하려는 브랜딩 지향인

---

## 2. 핵심 가치 및 목표 (Core Values & Goals)
1. **시각적 탁월함**: 모던하고 세련된 UI/UX 템플릿 제공으로 방문자에게 강렬한 첫인상 부여
2. **쉬운 관리**: 포트폴리오 프로젝트, 경력 정보, 블로그 글을 한 곳에서 편리하게 편집 및 발행
3. **높은 웹 성능 & SEO**: 빠른 로딩 속도와 검색 최적화를 통한 개인 인지도 극대화

---

## 3. 핵심 기능 요구사항 (Features)

### 3.1. 프로필 및 경력 카드 (Profile & Resume Card)
* **소개 영역**: 사용자 사진, 한 줄 소개(Title), 자기소개 상세 작성 가능.
* **소셜 링크 연동**: GitHub, LinkedIn, 이메일, 기술 블로그 URL 연결.
* **기술 스택 (Skills)**: 보유 직무 역량 카테고리별 분류 및 레벨(또는 태그) 표기.

### 3.2. 포트폴리오 프로젝트 관리 (Portfolio Showcase)
* **프로젝트 목록**: 대표 프로젝트 노출 여부(isFeatured) 설정, 카테고리별 필터링.
* **프로젝트 상세**:
  - 프로젝트 개요, 이미지, 주요 기여도, 성과 수치화 표기
  - 적용 기술 스택 태그 설정
  - 배포 URL(Live Link) 및 소스 코드 링크 연동

### 3.3. 블로그 & 아티클 작성 (Branding Blog)
* **마크다운 지원**: 마크다운 편집기를 활용한 가독성 높은 글 작성.
* **인사이트 분류**: 태그 시스템을 이용한 글 관리.
* **상태 관리**: 임시저장(Draft) 및 발행(Published) 상태 관리.

---

## 4. 데이터 모델 (Drizzle ORM Schema 구조)
기본 스택에 적용된 데이터베이스 스키마 구성:
* **users**: 사용자 기본 정보 (이름, 이메일 등)
* **profiles**: 사용자별 소셜 채널 및 바이오 정보
* **projects**: 포트폴리오 프로젝트 메타데이터 및 상세 내역
* **posts**: 셀프 브랜딩 아티클 및 블로그 아카이빙 데이터

---

## 1. 문서 목적

이 문서는 사업자가 광고대행사를 거치지 않고 **직접 마케팅 상품을 선택·설정·결제·실행하고 결과를 추적**할 수 있는 셀프 마케팅 플랫폼의 제품 요구사항을 정의한다. 아우라비즈, 리워드웍스, 플레이스연구소 등 기존 셀프 마케팅 서비스를 벤치마크로 하되, 우리 제품이 무엇을 만들고 무엇을 만들지 않을지를 분명히 한다.

이 문서가 다루는 것: 사용자 여정, 기능 요구사항, 데이터 모델, 운영/정산 구조, 컴플라이언스 원칙, MVP 범위.
이 문서가 다루지 않는 것: 상세 UI 시안, API 스펙 문서, 마케팅 카피, 가격표 확정.

## 2. 배경과 문제 정의

### 2.1 기존 광고대행 방식의 문제

전통적인 광고대행은 "업체 문의 → 상담 → 견적 → 계약 → 담당자 세팅 → 결과 보고" 흐름을 거친다. 소상공인·중소 셀러 입장에서 이 구조는 다음과 같은 마찰을 만든다.

- **진입 장벽이 높다.** 최소 계약 단위가 크고, 상담·계약에 시간이 걸린다.
- **가격이 불투명하다.** 동일 서비스도 대행사마다 견적이 다르고 거품이 끼기 쉽다.
- **소액·단발성 실행이 어렵다.** "10일만, 5만 원어치만" 같은 요구를 받아주는 곳이 드물다.
- **진행 상황이 깜깜하다.** 결과 보고서를 받기 전까지 무슨 일이 일어나는지 알기 어렵다.

### 2.2 솔루션 한 줄 정의

> **마케팅 서비스를 쇼핑몰에서 상품 사듯 직접 골라 실행하고, 진행 현황을 실시간 대시보드로 확인하는 셀프 서비스 플랫폼.**

사용자 흐름은 다음으로 단순화된다.

```
회원가입 → 서비스 선택 → 예산·키워드·기간 입력 → 결제 → 캠페인 자동 실행 → 대시보드에서 추적
```

### 2.3 제품 비전 / 목표

- 비전: 마케팅 실행을 "구매 가능한 상품"으로 표준화해, 누구나 대행사 없이 시작할 수 있게 한다.
- 1차 목표(6개월): 핵심 상품 3종(트래픽 유입 / 블로그 리뷰 / 플레이스 유입)으로 자가 주문 → 자동 실행 → 추적 루프를 완성한다.
- 2차 목표: 상품 카탈로그 확장 + AI 자동 세팅 + 양면 정산(매체·크리에이터)까지 운영 자동화.

|---|---|---|---|
| **로컬 자영업자** | 음식점·미용실·학원 등 오프라인 매장 운영 | 네이버 플레이스 노출·방문 유도 | 플레이스 유입, 방문자 리뷰, 블로그 리뷰 |
| **온라인 셀러** | 스마트스토어·쿠팡 판매자 | 상품 유입·찜·전환 보조 | 스토어 유입, 찜·알림받기, 체험단 리뷰 |

## 4. 핵심 가치 제안 / 차별점

1. **상품화된 마케팅** — 상담·계약 없이 카탈로그에서 바로 주문.
2. **투명한 단가·수량** — 단위당 단가, 예상 수량, 진행/잔여 수량을 모두 노출.
3. **실시간 추적** — 일별 유입량, 진행 상태, 사용 금액을 대시보드에서 확인.
4. **통합 계정** — 플레이스·스토어·바이럴·체험단·언론을 한 계정에서 관리.
5. **AI 자동 세팅(2차)** — 키워드/카테고리 데이터로 유입 수량·스케줄을 제안.

## 5. 사용자 여정 (End-to-End)

### 5.1 수요자(광고주) 여정

1. **회원가입/로그인** — 이메일 또는 소셜, 사업자 정보 입력(선택).
2. **상품 탐색** — 카탈로그에서 목적/업종별로 상품 필터링.
3. **캠페인 빌더** — 선택 상품에 따라 동적 입력 폼 노출(업체명, URL, 키워드, 지역, 수량, 기간, 미션 등).
4. **견적 미리보기** — 입력값 기반 예상 비용·예상 수량·예상 일정 자동 계산.
5. **결제** — PG 결제 또는 충전식 크레딧 차감.
6. **검수/승인** — 정책 위반·필수값 누락 자동 검증 → 운영 검수(필요 시).
7. **자동 실행** — 시스템이 캠페인을 공급 풀(매체/체험단/크리에이터)에 배정.
8. **추적** — 대시보드에서 진행/잔여 수량, 일별 유입, 상태, 리포트 확인.
9. **연장/재구매** — 캠페인 종료 시 원클릭 연장 또는 재주문.

### 5.2 공급자 여정 (2차)

매체/크리에이터 가입 → 가능한 캠페인 풀 확인/수락 → 미션 수행/콘텐츠 제출 → 검수 통과 → 정산.

### 5.3 운영자(어드민) 여정

상품/단가 관리 → 신규 캠페인 검수 → 공급 배정(자동/수동) → 진행 모니터링 → 이슈 처리(환불/일시정지) → 정산 마감.

## 6. 기능 요구사항

각 요구사항은 우선순위로 표기한다. **P0 = MVP 필수, P1 = 후속, P2 = 추후.**

### 6.1 마케팅 상품 카탈로그 (P0)

- 상품을 카테고리로 분류: 트래픽 유입 / 리뷰·체험단 / 바이럴 / 언론 / 인플루언서 / 순위추적.
- 각 상품은 **상품 타입(product type)** 을 가지며, 타입별로 캠페인 입력 폼 스키마가 다르다.
- 상품 카드에 표시: 명칭, 설명, 단위(1유입/1건/1일), 단가, 최소·최대 주문 수량, 예상 소요 기간, 주의사항.
- 업종/목적 필터(로컬 매장 / 온라인 스토어 / 신규 브랜드)와 검색.

**대표 상품 타입(초기)**

| 상품 타입 | 설명 | 단위 | 핵심 입력값 |
|---|---|---|---|
| `place_traffic` | 네이버 플레이스 유입 | 1유입/일 | 매장 URL, 키워드, 지역, 일 유입량, 기간, 미션(저장/길찾기) |
| `store_traffic` | 스마트스토어·쿠팡 유입 | 1유입/일 | 상품 URL, 키워드, 일 유입량, 기간 |
| `store_action` | 찜·알림받기 | 1건 | 상품 URL, 수량, 기간 |
| `blog_review` | 블로그 체험단/기자단 | 1건 | 상품/매장 정보, 가이드라인, 모집 인원, 기간 |
| `visit_review` | 방문자 리뷰 | 1건 | 매장 URL, 수량, 기간 |
| `community_viral` | 카페·커뮤니티 바이럴 | 1건 | 타겟 커뮤니티, 메시지 톤, 수량 |
| `pr_media` | 언론 보도 | 1건 | 보도자료, 희망 매체 수 |
| `influencer` | 인스타/유튜브/인플루언서 | 1건 | 채널 유형, 팔로워 구간, 콘텐츠 가이드 |
| `rank_tracking` | 순위 추적(부가) | 구독 | 매장/상품 URL, 추적 키워드 |

### 6.2 캠페인 빌더 (P0)

- 상품 타입별 **동적 폼**(스키마 기반 렌더링). 타입마다 필요한 필드만 노출.
- **실시간 견적 계산**: `예상 비용 = 단가 × 수량 × 기간` 형태로 입력 변경 시 즉시 갱신.
- **입력 검증**: URL 형식, 키워드 길이, 최소/최대 수량, 일 유입량 상한 등.
- **임시 저장(Draft)**: 결제 전 캠페인을 저장하고 나중에 이어서 진행.
- (P1) **AI 추천**: 키워드/카테고리 입력 시 권장 유입 수량과 스케줄 자동 제안. 사용자는 제안값을 수정 가능.

### 6.3 결제·크레딧 (P0)

- 두 가지 모델 지원(택1 또는 병행):
  - **건별 결제**: 캠페인 단위로 PG 결제.
  - **크레딧 충전**: 선충전 후 캠페인마다 차감(소액·반복 주문에 유리).
- 결제 수단: 카드, 계좌이체/가상계좌(국내 PG: 토스페이먼츠/포트원 등 후보).
- 세금계산서/현금영수증 발행 정보 입력.
- 환불 정책: 미실행분 환불 규칙, 부분 진행 시 잔여분 환불·크레딧 전환.

### 6.4 검수·자동 실행 엔진 (P0)

- **자동 검증**: 결제 직후 정책 위반 키워드, 금지 업종, 필수값 누락 검사.
- **공급 배정**: 캠페인을 공급 풀에 분배. MVP는 운영자 수동 배정 + 큐(queue), 2차에서 규칙 기반 자동 배정.
- **스케줄러**: 일 단위 유입량을 기간에 맞춰 분산 실행(평탄화). 주말/심야 비중 조정 옵션(P1).
- **상태 머신**: `draft → submitted → reviewing → scheduled → running → paused → completed / canceled / refunded`.

### 6.5 대시보드·리포트 (P0)

- 캠페인별 카드: 상태, 진행 수량 / 잔여 수량(진행률 바), 일별 유입 그래프, 사용 금액, 시작·종료일.
- 전체 요약: 진행 중 캠페인 수, 총 집행 금액, 누적 유입.
- 일별 데이터 다운로드(CSV).
- (P1) 외부 지표 연동 또는 순위 추적 결과 동반 표시.
- **종료 시 액션**: 연장 / 재구매 버튼.

### 6.6 회원·계정 (P0)

- 가입/로그인(이메일·소셜), 비밀번호 재설정.
- 프로필: 사업자 정보, 결제수단, 발행 정보.
- 내 캠페인 목록, 주문/결제 내역, 크레딧 잔액.
- (P1) 다중 매장/상품 관리(하나의 계정에 여러 비즈니스 등록).

### 6.7 매니저 지원 (P1)

- 채팅/문의 채널(채널톡 등 연동) — 셀프 실행을 기본으로 하되 막힐 때 도움.
- 전담 매니저 배정(상위 플랜 한정).

### 6.8 운영자(어드민) (P0 일부)

- 상품·단가·재고(공급 가용량) 관리.
- 캠페인 검수 큐, 수동 배정/일시정지/취소/환불.
- 공급 풀 관리(매체·체험단·크리에이터 등록·상태).
- (P1) 정산 모듈: 공급자별 수행량 집계 → 정산서 생성.
- (P1) 운영 지표 대시보드(GMV, 캠페인 수, 완료율, 환불율).

### 6.9 공급자 포털 (P2)

- 공급자 가입/심사, 캠페인 수락, 결과물 제출, 정산 내역 확인.

## 7. 비기능 요구사항

- **성능**: 대시보드 주요 화면 LCP 2.5초 이내. 일별 집계는 배치/캐시.
- **보안**: 개인정보·결제정보 암호화, 접근권한(RLS) 분리, 결제 정보는 PG 토큰화(카드번호 비저장).
- **확장성**: 상품 타입 추가가 코드 변경 없이 스키마/설정으로 가능하도록 설계.
- **감사성**: 캠페인 상태 변경·금액 변동 이력 로깅.
- **가용성**: 결제·주문 트랜잭션 무결성 보장(중복 결제 방지, 멱등 처리).
- **접근성/반응형**: 모바일 우선. 자영업자 다수가 모바일로 주문.

## 8. 데이터 모델 (개략, Postgres/Supabase 기준)

> 핵심 테이블만. 실제 구현 시 인덱스·제약·RLS 정책 별도 정의.

```
users
  id (uuid, pk)
  email, name, phone
  role (advertiser | supplier | admin)
  created_at

businesses                     -- 한 유저가 여러 매장/상품 보유 가능
  id (uuid, pk)
  user_id (fk → users)
  type (place | store)         -- 매장 / 온라인스토어
  name
  external_url                 -- 플레이스/스토어 URL
  meta (jsonb)
  created_at

products                        -- 판매되는 마케팅 상품(카탈로그)
  id (uuid, pk)
  product_type (enum)          -- place_traffic, blog_review ...
  title, description
  unit (enum)                  -- per_visit_day | per_item | subscription
  unit_price (numeric)
  min_qty, max_qty
  est_duration_days
  form_schema (jsonb)          -- 캠페인 빌더 동적 폼 정의
  is_active (bool)

campaigns
  id (uuid, pk)
  user_id (fk → users)
  business_id (fk → businesses)
  product_id (fk → products)
  status (enum)                -- draft → ... → completed/refunded
  inputs (jsonb)               -- 키워드/지역/미션 등 폼 입력값
  daily_qty, total_qty
  start_date, end_date
  quoted_amount (numeric)
  paid_amount (numeric)
  created_at, updated_at

campaign_events                 -- 일별 실행/유입 기록(추적용)
  id (pk)
  campaign_id (fk)
  event_date (date)
  delivered_qty (int)
  created_at

orders / payments
  id (pk)
  user_id (fk)
  campaign_id (fk, nullable)   -- 크레딧 충전은 null 가능
  amount, method, pg_tx_id
  status (paid | refunded | partial_refund)
  created_at

credits                         -- 크레딧 잔액/원장
  id (pk)
  user_id (fk)
  delta (numeric)              -- +충전 / -차감
  reason, ref_id
  created_at

suppliers                       -- 공급 측(매체/체험단/크리에이터)
  id (pk)
  user_id (fk → users)
  channel_type
  capacity, status

assignments                     -- 캠페인 ↔ 공급자 배정
  id (pk)
  campaign_id (fk)
  supplier_id (fk)
  assigned_qty
  status (assigned | in_progress | submitted | approved | rejected)

settlements                     -- 정산(2차)
  id (pk)
  supplier_id (fk)
  period
  amount
  status
```

상태 전이 요약:

```
draft → submitted → reviewing → scheduled → running → completed
                              ↘ rejected
running → paused → running
running/scheduled → canceled / refunded
```

## 9. 기술 스택 / 아키텍처 (제안)

- **프론트엔드**: Next.js (App Router) + Tailwind, Vercel 배포.
- **백엔드/DB**: Supabase (Postgres + Auth + Row Level Security + Storage).
- **결제**: 포트원(아임포트) 또는 토스페이먼츠 연동. PG 토큰화로 카드정보 비저장.
- **스케줄러/배치**: 일별 유입 분산·집계는 Supabase Edge Functions + cron(또는 Vercel Cron).
- **자동 배정 엔진**: 초기에는 운영자 큐 기반, 이후 규칙 엔진으로 단계 확장.
- **버전관리/배포**: GitHub → Vercel CI/CD.

> 이 스택은 헤나님이 이미 사용 중인 Claude Code → GitHub → Vercel → Supabase 흐름과 그대로 맞물린다.

## 10. 컴플라이언스 / 리스크 (중요)

이 영역은 제품의 생존과 직결되므로 별도 강조한다.

### 10.1 표현 가이드 (필수 준수)

- 네이버·쿠팡 등 외부 플랫폼의 노출/순위 정책은 수시로 변경된다.
- 따라서 **"순위 보장", "1페이지 확정", "노출 100% 보장"** 류의 확정적 표현을 제품 카피·상품 설명·약관 어디에도 쓰지 않는다.
- 대신 **"유입 지원", "마케팅 활동 지원", "노출 기회 확대"** 등 활동 기반 표현을 사용한다.

### 10.2 플랫폼 정책 리스크

- 리워드/트래픽 상품은 외부 플랫폼의 어뷰징 탐지·정책 변경에 따라 효과·지속성이 영향을 받을 수 있다.
- 정책 변동에 대비해 **상품 활성/비활성 토글**, **공급 방식 교체 용이성**을 설계에 반영한다.
- 약관에 외부 플랫폼 정책 변경에 따른 면책·환불 기준을 명시한다.

### 10.3 제품 한계의 명시

- 셀프 마케팅 플랫폼은 **실행 도구**다. 다음은 자동으로 해결되지 않으며, 이를 사용자에게 솔직히 안내한다.
  - 상품 가격 경쟁력, 리뷰 수·평점, 썸네일/상세페이지 품질, 구매 전환율, 재구매 구조, 브랜드 신뢰도.
- 즉 "유입은 만들 수 있어도 전환은 상품·페이지 경쟁력에 달려 있다"는 점을 온보딩·상품 설명에서 명확히 한다.

### 10.4 법무/운영

- 전자상거래법상 환불·청약철회 규정, 세금계산서 발행, 개인정보 처리방침 준비.
- 금지 업종/불법 키워드 필터링 정책 수립.
